## How to run

pull the repo

```bash
git clone https://github.com/cER002/CMP309-LAB08.git
```

install project dependencies and run the app

- npm

```bash
npm install
npm run start
```

- yarn

```bash
yarn install
yarn start
```

- pnpm

```bash
pnpm install
pnpm start
```

- bun

```bash
bun install
bun run start
```

## Reasoning Questions

- **Q1:** Every single API test and page returned 404 catch all respone. Since path are evaluated from top the bottom, a single catch-all path just shadowed all the other more specific ones.

- **Q2:** None of the promises returned by `fetch(...)` was able to resolve. Request/Respone cycle was not completed and the browser just kept waiting. Trying to reach any page directly causes the browser to show loading icon indefinitely. But the logger still went off because it is called after the `requestCounter` but none of the routes were reached

- **Q3:** 201 was chosen because it means "created" which is more fitting for subscribing, it signals that something was created on the server side to the client, status code 200 just means a generic success. 404 directly tells the client that the page is not found, it is more reliable than trying to make sense of a random error message sent with status code 200 because it's much more predictable and machine-readable

- **Q4:** Using `process.env.PORT` is important instead of hardcoding a port like 3000. Assigning a port through the environment is easier for deployment. The `?? 3000` fallback is also good for developers.

- **Q5:** node_modules stores the dependencies of the application, it can be a very large folder and the dependencies are most likely in NPM's repository, so it does not make sense to even add them to version control. A teammate simply can use the tool of their choice to install the depedencies after cloning the repository like `npm install`

- **Q6:** Due to Same origin policy the external scripts, `app.js` in this case, were blocked from loading to prevent security issues, without the client-side code only the HTML and the style sheets would load which causes the API endpoints to not work at all

## Self-Study

- Node version and server uptime (in seconds) can be access from the `process` variable with `.version` and `uptime()`

- Content type can be set for the respone with `res.type(...)` or `res.set({' Content-Type': '...' })`

- The indentation parameter in `JSON.stringify()` allows it to be prettified (eg. `JSON.stringify(..., null, 4)`)

- While trying to get the body of the respone to be rendered, `res.body` and `res.text` return ReadableStream and Promise objects respectively, not properly cosuming the stream or resolving the promise ends up with broken UI

- While inspecting the Network tab, I have learned that browsers check if the content that's being served by the server has changed or not to save bandwidth

- While inspecting `/api/stats`, having the Network monitor open triggered twice the amount of requests, appearently it causes fetches on itw own too
